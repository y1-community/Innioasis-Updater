The dark display after a restart

The owner's over-the-air update to Beta 8.3 restarted from the recovery into a dark display; Reborn never drew a frame and the health check rolled the update back (Beta 8.3 report). Four restarts from the recovery that day, logs in out/dsi-lag-2026-10-18/ (local):

Bootholding SMI common/larb0 at mm-clocks probe (0.36 s)Handover snapshotDisplay
6500 install, 6501 install, rollback (8.2)yeslarb0 stat=0 greq=0lit
6600 install (8.3)noSMI gates 1 left closed by a restart, larb0 stat=1 greq=1 after 10 msdark
rollback to 6500 (8.3's recovery)yeslarb0 idlelit

On the dark boot the SMI common clock gate was closed before Linux touched anything (before Lima's probe at 0.39 s), and LK's display request was stuck in larb0. The DSI register reads lagging one register from the first modeset, which three DSI power cycles did not clear, are the consequence. This is the case found in POWER-FINAL-40: a watchdog restart keeps MMSYS_CG_CON0, so a gate Linux closed at shutdown (DRM disables the display and drops its SMI references) reaches LK, and LK's first fetch through larb0 never completes. 42 reopened the gates as the last step of a restart; 43 removed that because its own test restarts were dark for a second reason (Lima closing the gate during the next boot), which 43's hold fixes. Since then nothing covered the first case.

PartChange (Linux 7ed664b)
Restart handlerBack: priority 255, after every driver has shut down and before the watchdog handler (128); writes MMSYS_CG_CLR0 = 3 (SMI common, larb0) when the DIS domain is powered. A powered-down domain comes back with its gates open anyway.
HoldUnchanged (43): mm-clocks holds SMI common/larb0 from probe until the display mutex owns them.
EvidenceWhen the gate is found closed at probe, the boot logs SMI common gated before Linux touched it: CG_CON0=… larb0 stat=… greq=….
Testtests.test_display_domain: the handler writes only MMSYS_CG_CLR0 = 3 and only with DIS powered; registered after the hold.

Not established: why only some restarts leave the gate closed; the handler reopens it on every restart either way.

The first OTA to 8.4: the restart into the recovery is still done by the running 8.2/8.3 kernel, so the install screen can stay dark once more; the restart out of the recovery into 8.4 is done by 8.4's recovery kernel, which has the handler.

Install (kept 6600 package as the rollback copy, source: package), journal timings: verify 1.50 s (the kept root hashed alongside), backup_root 0.17 s, backup_boot 1.31 s, system 8.33 s, check 4.10 s, boot 0.76 s: 16.2 s. The estimate said 14 s at verify, 8 s at system (real 12.8 s), 7 s at check (4.9), 1 s at boot (0.8): the system write took 8.3 s for 103 MB written, against 4.4 s for the same amount in the 6600 install, so the model's 10 ms per MiB was low this time (eMMC write speed varies; one sample).

One lit restart through the handler is not yet proof for an intermittent fault (one dark restart in five that day).
