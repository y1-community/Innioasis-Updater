MT6582 hardware video decoder: what the stock firmware does

Status: reverse-engineering notes, 2026-11-12 (video plan step 1). Read from the stock y2_v3.2.0_FM-20260813 kernel (out/rea/fm-kernel.elf, symbols present) and from /system/lib/libvcodecdrv.so (not stripped; decompiled with Ghidra into out/rea/video/decomp/vcodecdrv/, one file per function). Nothing in this file has run on the player unless a line says so; the bring-up section near the end is measured.

Extraction: system.img is an Android sparse image; convert it to raw, then debugfs -R "dump /lib/libvcodecdrv.so libvcodecdrv.so" system.raw. Ghidra loads the library at 0x10000, so a DAT_000xxxxx literal sits at file address xxxxx - 0x10000.

Power domain on (spm_mtcmos_ctrl_vdec(1)), all on VDE_PWR_CON: set PWR_ON (bit 2), set PWR_ON_S (bit 3), wait until bit 7 is set in both status registers, clear PWR_CLK_DIS (bit 4), clear PWR_ISO (bit 1), set PWR_RST_B (bit 0), clear SRAM_PDN (bits 8..11), wait until SRAM_PDN_ACK (bit 12) reads 0. Then stock restores the larb registers (larb_restore). Off is the mirror: set SRAM_PDN, wait for ack, set PWR_ISO, clear PWR_RST_B and set PWR_CLK_DIS, clear PWR_ON and PWR_ON_S, wait until bit 7 is clear in both.

Interrupt handler (dec_isr): the status is MISC+0xa4 bit 16. Acknowledge: set bits 0 and 4 (|= 0x11), then clear bit 4. The handler then wakes the waiting decoder thread; nothing else happens in the kernel.

The stock kernel driver does nothing else for decoding: a lock (one decoder user at a time; taking it switches the clocks on and enables the interrupt, releasing it switches them off), wait-for-interrupt with a timeout, and mmap of the registers into the process. All decoding logic is in userspace.

vcodec_mmap also admits 0x10000000..0x10001000 and 0x10004000..0x10005000 (clock blocks, read by the library for debugging) and a 0x07fff000/0x08000000 range (not needed).

This is the same block layout mainline Linux names VDEC_SYS/MISC/LD/TOP/CM/AD/AV/PP for the later MT8173 decoder (mtk_vcodec_dec), and the interrupt acknowledge (0xa4, 0x11, 0x10) is the same too. Per picture (FUN_0001afc0), after the access unit's NAL units are in the bitstream buffer, each with a 3-byte start code, and 00 00 00 01 appended after the last one:

  1. Lock (kernel: clocks on, interrupt enabled).
  2. H264_HAL_ResetHW: wait while VLD+0xf4 bit 15 is set until bit 0 sets (50 000 tries); VLD+0x108 = 0x101;

    SYS+0x0 = 1; MISC+0xf4 &= ~1; MISC+0x84 = 2; MISC+0x0 = (old & 0xff400000) | 0x00801ff0; MISC+0xc8 = 0xf7; MISC+0xcc = 0x13a20100; VLD+0x108 = 0; SYS+0x18 = 1; MISC+0xec = 1. Then (InitVDecHW) AVC_VLD+0x280 = 0xbfdfb2f7 (error mask).

  3. H264_HAL_InitH264BarrelShift: VLD+0xc0 = 0x40000; AVC_VLD+0x84 = 0xae00e007; VLD_TOP+0x54 |= 1;

    MC+0x24 = 6; VLD+0xb4 = start >> 6; VLD+0xb8 = (start + size + 0x100) >> 6; VLD_TOP+0x28 = work; AVC_VLD+0x28c = 1 then 0. Then (…BarrelShifterAlign) wait on VLD+0xf4 as in step 2; VLD+0x110 |= 1; VLD+0xb0 = start (twice); VLD+0x110 = end; AVC_VLD+0x28c = 1; VLD+0x108 = 0x100 then 0; VLD+0xcc = 0; VLD+0x8c = 0x100000; wait until VLD+0xe8 bit 0 is set (4096 tries; SYS+0x0 must read 0x111); VLD+0x8c = 0x800000; AVC_VLD+0x28c = 0; read AVC_VLD+0x0.

  4. H264_HAL_GetStartCode_8530: read AVC_VLD+0x0 (the next 32 bits, nothing consumed). When it is not

    00 00 01 xx, AVC_VLD+0x2d8 = 1 and wait until bit 0 clears. Then consume 32 bits (start code and NAL header).

  5. parseSliceHeaderHW walks the first slice header through the hardware's bit reader, which removes

    emulation-prevention bytes itself: reading AVC_VLD + 4*n returns the next 32 bits and consumes n bits (n = 0 only looks); reading AVC_VLD+0x23c returns and consumes one ue, AVC_VLD+0x240 one se. Order: first_mb ue, slice_type ue, pps_id ue, colour_plane (2 bits, if separate planes), frame_num, field_pic and bottom_field flags (if not frame_mbs_only), idr_pic_id ue (IDR), pic_order_cnt_lsb and delta_pic_order_cnt_bottom se, or delta_pic_order_cnt[0..1] se, redundant_pic_cnt ue, direct_spatial_mv_pred (B), num_ref_idx_override and the two counts (clamped to 31). Here the picture registers are written (step 6), then: - reference list modification: AVC_VLD+0x22c = 1, wait until it reads non-zero (1.5 ms limit): the hardware reads the syntax and reorders its own lists; - prediction weight table (weighted P, or B with bipred idc 1): MISC+0xf0 |= 1, AVC_VLD+0x230 = 1, wait until it reads non-zero, then AVC_VLD+0xf0 = (old MISC+0xf0) & ~1 (as the library does); - dec_ref_pic_marking (if nal_ref_idc): read flag by flag and ue by ue; - cabac_init_idc ue (CABAC, not I/SI), slice_qp_delta se, SP/SI fields, deblocking fields, slice group change cycle.

  6. Vdec_Drv_setDecPicInfo:
    • H264_HAL_InitPRefList: MC+0x564 = 0; AVC_VLD+0x228 = 1, wait until bit 0 clears;

      AVC_VLD+0xa0 = MaxFrameNum (×2 for a field); AVC_VLD+0xa4 = CurrPicNum.

    • defaults: MC+0x3dc + 4i (i < 32) = current Y address; AVC_MV+0x180 + 4i = current MV buffer >> 4.
    • P list entry i (initial order of the standard: short-term by PicNum descending, then long-term by

      LongTermPicNum ascending), frame decoding: MC+0x3dc + 4i = Y address; AVC_VLD+0xa8 + 4i = long << 19 | (FrameNumWrap or LongTermFrameIdx) & 0x7ffff; AVC_MV + 8i = `buffer index << 23 | long << 20 | (top POC <= bottom POC) << 21 | top flags;AVC_MV + 8i + 4` = the same with bit 22 set and the bottom flags. Field flags: 0x80000 when the reference was coded as a field, 0x40000 when it was an MBAFF frame.

    • H264_HAL_SetPOC: AVC_MV+0x200 = POC of the picture (frame: the smaller field POC), frame also

      AVC_MV+0x204 = top POC, +0x208 = bottom POC, each & 0x3ffff.

    • B lists (MC+0x568 = 0, MC+0x56c = 0; defaults MC+0x45c + 4i and MC+0x4dc + 4i = current Y):

      entry i of list 0: MC+0x45c + 4i, AVC_VLD+0x128 + 4i, AVC_MV+0x80 + 8i / +0x84 + 8i with the field POC & 0x3ffff added to the P format; list 1: MC+0x4dc + 4i, AVC_VLD+0x1a8 + 4i, AVC_MV+0x100 + 8i / +0x104 + 8i, and the co-located motion vectors AVC_MV+0x180 + 8i = MV buffer >> 4, AVC_MV+0x184 + 8i = that + 4 (2 and AVC_MV+0x220 |= 0x20 with direct_8x8_inference). When list 1 equals list 0 and has more than one entry, entries 0 and 1 of list 1 are swapped (H264_HAL_B1ListSwap).

    • scaling lists (H264_HAL_WriteScalingList), raster order, four bytes per word, first byte in bits 31..24:

      for word k of list n: VLD+0x260 = a + 0x200, VLD+0x264 = word, VLD+0x260 = a + 0x100, with a = 16n + 4k for the six 4×4 lists, 0x60 + 4k and 0xa0 + 4k for the two 8×8 lists.

    • H264_HAL_SetSPSAVLD: AVC_VLD+0x88 = chroma_format_idc | 0x200000 | log2_max_frame_num_minus4 << 2 |

      poc_type << 6 | log2_max_poc_lsb_minus4 << 8 | delta_pic_order_always_zero << 12 | num_ref_frames << 13 | frame_mbs_only << 18 | mbaff << 19 | direct_8x8_inference << 20; VLD_TOP+0x68 = (width in MBs − 1) | (height in map units − 1) << 16.

    • H264_HAL_SetPPSAVLD: AVC_VLD+0x90 = cabac | pic_order_present << 1 | weighted_pred << 2 |

      weighted_bipred_idc << 3 | (pic_init_qp − 26 & 0x3f) << 5 | (chroma_qp_offset & 0x1f) << 11 | deblocking_control_present << 16 | constrained_intra_pred << 17 | transform_8x8 << 18 | (second_chroma_qp_offset & 0x1f) << 19; AVC_VLD+0x94 = default l0 count − 1 | (default l1 count − 1) << 5 | per-list scaling flags in bits 10..17 | scaling enabled << 18.

    • H264_HAL_SetSHDRAVLD1: AVC_VLD+0x8c = (old & 0xfffe0000) | first_mb & 0x1fff; AVC_VLD+0x98 =

      (old & 0x1fff) | slice_type << 13 | field_pic << 17 | bottom_field << 18 | direct_spatial << 19 | (l0 count − 1) << 20 | (l1 count − 1) << 25.

  7. H264_HAL_DecStart: MISC+0x4 = 3; MC+0x90 = 4; VLD_TOP+0x58 = ~0; MC+0x208 = width;

    MC+0x20c = height; AVC_VLD+0x280 = 0xbfdfb2f7; MC+0x220 = 1; MC+0x224 = Y >> 9; MC+0x228 = (Y + Ysize) >> 8; MC+0x250 = 1; MC+0x238 = 3; MC+0x260 = MBs wide − 1; MC+0x264 = MBs high − 1; MC+0x22c = MBs wide; MC+0x850 = (Y + Ysize*3/2) >> 4; MC+0x854 = Y >> 4; MC+0x858 = 1; MC+0x5e4 = 0x20000; MC+0x560 = Y; MC+0x55c = Ysize; MC+0x980 = MBs wide; AVC_VLD+0x2c8 = 0xf9040039; AVC_MV+0x20c = MV buffer >> 4; AVC_VLD+0x9c = slice_qp_delta & 0x7f | disable_deblocking_idc << 7 | (alpha offset & 0xf) << 9 | (beta offset & 0xf) << 13 | nal_ref_idc << 17 | IDR << 19 | cabac_init_idc << 20; with CABAC AVC_VLD+0x234 = 1; wait until AVC_VLD+0x25c bit 25 clears; MC+0x5e4 |= 0x1000; MC+0x768 = (old & ~7) | 4; MISC+0xf0 |= 1; VLD_TOP+0x6c = macroblocks in the picture; VLD_TOP+0x50 = ~0; MC+0xa20 = work B; MC+0xa24 = work A; AVC_VLD+0x2d0 = 0x103; AVC_VLD+0x2d4 = 0xc210; MISC+0x28 |= 1; MISC+0x3c = Y and MISC+0x40 = Y + Ysize*3/2 (the range the picture may be written to); MISC+0x54 = lowest MV buffer address and MISC+0x58 = end of the highest (same for motion vectors); AVC_VLD+0x84 = 0xae00e007; AVC_VLD+0x238 = 1 starts the decode.

  8. Wait for the interrupt (one per picture: the hardware reads the following slices of the buffer itself).

    Result: AVC_VLD+0x284 & AVC_VLD+0x280 is the error word (0 = good), AVC_VLD+0x278 bit 31 = picture complete, MC+0x28 / MC+0x2c = macroblock position reached.

  9. Unlock (clocks off).

The library's own DPB bookkeeping (frame-number gaps, sliding window, MMCO, output order) is ordinary H.264 and is not copied: FFmpeg does that part for us.

Limit seen in the library: H264_CheckHWParameter and Vdec_Drv_H264_open refuse more than 0x1fe000 luma samples (1920×1088) and less than 64 in either direction.

Bring-up on the owner's player, 2026-11-12 (test builds 236 and 237)

Measured on the player, kernel 6.18.56-y2linux-1.0.0-beta.9.3.24 with kernel/platform/vdec.c:

  • Power: after the domain sequence and the two clock-enable writes SYS+0x0 reads 0x111 and SYS+0x8 reads

    0x1; the decoder's registers answer (MISC+0xa4 = 0x1000, MISC+0xc8 = MISC+0xcc = 0xffffffff after power-up). Power-off and repeated cycles are clean. CLK_CFG_1 reads 0x00810100: the loader left the decoder's mux on source 1 (VENCPLL), which the display keeps running.

  • Memory: the decoder reads the bitstream and writes pictures at plain physical addresses; the M4U is not

    needed and no IOMMU driver exists or is planned.

  • The hardware's bit reader returns 0x00000165 for a buffer starting 00 00 01 65, and AVC_VLD+0x84 reads

    back 0x2e00c007 (bit 31 clear), so the start-code search of step 4 is skipped when the reader already stands on a start code. Searching anyway runs on to the next start code and loses the picture (the one mistake of the first driver version).

  • Decoding: 95 pictures in six test streams (x264: intra CAVLC and CABAC at 320×240; P with one and with three

    references and weighted prediction; B pictures; 1280×720 with four slices per picture) decode with error word 0 and are byte-identical to FFmpeg's software decoding after the block layout is unpacked (tools/development/vdec/compare.py). The layout is as read: luma in 16×32 blocks, CbCr in 16×16 blocks.

  • These runs used the bench vdec-lab (the driver's vdec-h264.c compiled into a userspace program that

    reaches the registers through the driver's debugfs file). The kernel's own call path with the corrected start-code step is checked with the next kernel build.

Through FFmpeg (test build 238, same day)

With our FFmpeg path (buildroot/patches/ffmpeg, hwaccel h264_y2vdec) and the driver's normal call: tools/development/vdec/vdec-ffmpeg.c decodes each file once on the hardware and once in software and compares every picture. Nine x264 files, 780 pictures, none differs: Baseline CAVLC 854×480 with three slices; Main 1280×720 with B pictures; High 1920×1080; High 1280×720 with a B pyramid, six references and weighted prediction; High 720×576 with the JVT quantisation matrices; 426×240 (cropped); 360×640; 176×144 with 16 references; 640×480 without B pictures (picture order type 2). An interlaced 720×576 file is refused by the hardware path at start and plays in software. One 1280×720 picture takes about 4 ms in the driver call (vdec-run: 30 pictures, 4.11 ms each), a 640×368 picture 1.2 ms.

Fields, MBAFF and the conformance streams (test build 245, same day)

The driver also decodes field pictures and MBAFF frames: reference lists per field parity as the stock library builds them (a field entry has one word in AVC_MV + 4i, bit 22 and a bit in MC+0x564/0x568/0x56c for a bottom field, PicNum 2 * FrameNumWrap + 1 for the parity being decoded), 0x80000 in the word of a reference coded as fields and 0x40000 for one coded as an MBAFF frame, MaxFrameNum * 2 and `CurrPicNum = 2 * frame_num

  • 1for a field, half the macroblock rows inMC+0x264andVLD_TOP+0x6c`, the bottom field's motion vectors

at the frame's buffer plus 4 (2 with direct_8x8_inference), and only the field's own picture order in AVC_MV+0x200.

The public JVT conformance streams (FFmpeg's FATE copy, h264-conformance/, remuxed to Matroska) were each decoded on the hardware and in software by vdec-ffmpeg on the player: **130 of 135 are identical in every picture**, among them the field, PAFF, MBAFF, long-term reference, reference marking and weighted prediction streams. The others: sp1_bt_a and sp2_bt_b (SP slices) and FM1_FT_E (slice groups) are Extended-profile features the hardware reports as errors; CVFC1_Sony_C (frame cropping at the top and left) decodes, the comparison tool and Reborn's picture conversion do not shift by the crop offset yet; one stream was refused by the hardware path at start and decoded in software. Per-file results: video-h264-conformance-245.txt. The High-profile part of the suite (FRExt/) has not been run.

MPEG-4 Part 2 (read out and brought up 2026-11-12)

Source: mpeg4_part2_risc_settings (the picture), eBufInitBS in libvcodec_utility.so (the bit reader), mpeg4_parse_VOL/mpeg4_parse_VOP (which header field goes where), mpeg4_dec_init (buffers). The library builds a list of register operations and hands it to eHalCmdProc; eVDecDrvQueryCapability(3) returns chip type 6 (VAL_CHIP_NAME_MT6582), and the list below is that branch. The library parses VOL and VOP headers itself; the hardware starts at the first macroblock and reads video packet headers on its own.

Working memory (stock sizes): prediction rows 0x20000 at VLD_TOP+0x28; a row buffer of (width in MBs) × 256 bytes at MC+0xa24; the map of macroblocks that were not coded at VLD+0x2d4; a second side buffer of 64 bytes a macroblock at VLD+0x2d8 (never written in our runs); the reference's motion vectors, 32 bytes a macroblock, at MV+0x20c (address >> 4). The map and the vectors are written by a P picture and read by the B pictures after it, so they live in memory across the per-picture reset (and across our power-off).

One picture:

  1. Reset: VLD+0x108 = 0x101; MISC+0xc8 = 0xfd; MISC+0xcc = 0x3e5a1108; MISC+0xf4 = 0; MISC+0x84 = 1;

    VLD+0x108 = 0; SYS+0x18 = 1; MISC+0xec = 1; MISC+0x4 = 1.

  2. Direct mode (MV): +0x2e0 = TRD | TRB << 16 (ticks between the references, and from the forward

    reference to this picture); +0x2e4/8/c the same in fields, and that ± 1; +0x2f0…+0x2fc the matching 14-bit ratios (TRD − TRB) << 14 / TRD | (TRB << 14 / TRD) << 16; +0x2d8 = quarter_sample | top_field_first << 1; +0x2dc = sprite vector (0); +0x20c = vector buffer >> 4; +0x218 bit 0 = this is a B picture and its backward reference is an I picture.

  3. Motion compensation (MC): +0x1fc = 1; +0x200 = quarter_sample; +0x204 = vop_rounding_type;

    +0x208/+0x20c = coded width/height (multiples of 16; the picture's own size only for old DivX builds); +0x21c = 0; +0x0/+0x4 reference 1 luma >> 9 / chroma >> 8, +0x8/+0xc reference 2, +0x9c/+0xa0 the B place; +0x24 = where to decode: 0 or 1 = that reference, 4 = the B place; +0x18 = which reference is the forward one. +0xa2c bit 28 = width ≤ 176; +0x920 |= 1 << 24; +0x980 = width in MBs; PP+0x3c |= 1 << 28; +0x220 = 1 with +0x224/+0x228 = the display frame, +0x22c = width in MBs, +0x700 = 0, +0x238 = 3, +0x250 = 0, +0x658 &= ~1, +0x260/+0x264 = last MB column/row, +0xa24 = row buffer.

  4. Quantiser matrices (quant_type 1): 16 times VLD+0x260 = 4i (inter: 0x40 + 4i), VLD+0x264 = four

    bytes of the matrix in stream (zigzag) order, first byte highest; then VLD+0x104 = 0x100 (inter 0x200).

  5. Parser (VLD): +0x1e8 = (old & 0xfffffefc) | 0x100, | 3 for a B picture behind an I picture (| 1 behind a

    sprite picture); +0x1c8 = 0x10001; +0x88 = top_field_first << 26 | vop_coding_type << 21 | alternate_scan << 17 | fcode_forward << 12 | fcode_backward << 4; +0x1c4 = (old & 0xf8070000) | resync_marker_disable << 26 | quarter_sample << 25 | quant_type << 24 | interlaced << 22 | data_partitioned << 21 | reversible_vlc << 20 (not in B) | vop_time_increment_resolution; +0x1d8 = 0; +0x1d4 = vop_quant | intra_dc_vlc_thr << 8; +0x90 = +0x94 = 0x1ff; VLD_TOP+0x68 = last MB column | last MB row << 16; VLD_TOP+0x70 = (width + 15) | (height + 15) << 16; the buffers; then for a picture wider than 176: +0x2dc = map bytes >> 4 | (6 × width >> 4) << 16, VLD_TOP+0x94 = prediction rows + 6 × width − 16, VLD_TOP+0x2c bit 30 = 0, VLD_TOP+0x40 bits 4–5 = 0, +0x2d0 = (old & ~4) | 0x80, +0x2e0 |= 2 (narrower: +0x2dc high half = width >> 1, PP+0x800 |= 0x100, VLD_TOP+0x2c bit 30, VLD_TOP+0x40 = 0x20, +0x2d0 |= 0x84). +0x1fc = 0x31; +0x2f8 &= 0xfffff7bf; +0x1d0 = 0x100.

  6. Bit reader (eBufInitBS): read VLD+0xf4; +0xb4 = start >> 6; +0xb8 = (end >> 6) + 12; +0xb0 =

    start; +0x110 = end + 0x300; +0x108 = 0x100, = 0; +0x1d0 |= 0x100; +0x8c = 0x100000; wait for +0xe8 bit 0; +0x8c = 0x800000; then step over the VOP header by reading VLD + 4n (n ≤ 24 bits a read). A header longer than 512 bits is shortened by starting 64 bytes later for every 512 bits. The library puts three VOP start codes behind the picture.

  7. Start: VLD+0x1cc = 1, 0; +0x1d0 = 1, 0; +0x8c = 0x8000000; +0x1d0 = 0; VLD_TOP+0x44 = ~0;

The interrupt is the same as for H.264.

  8. After: MISC+0xc8 = 0xfd; MISC+0xcc = 0x3e6a1108; SYS+0x0 = 1. VLD+0x3cc bit 8 = error (a good

    picture reads 0x02000000, a failed one 0x02010101); MC+0x28/+0x2c = last macroblock; VLD+0xfc = where the reader stopped.

What we do differently, and what the hardware does (bench vdec-lab with mpeg4_jobs.py, test build 245 kernel, pictures compared with FFmpeg):

  • The stock library shows a deblocked copy. With MC+0x220 = 1 the post-processing stage writes a second

    frame, and that one is filtered: 10 % of the samples differ from FFmpeg's, up to 7 levels. The stock library decodes into three fixed frames and shows only the copy. With MC+0x220 = 0 the frame that motion compensation writes is the picture, in the same block layout as H.264, and it is what the standard decodes. Our driver uses that: no copy, no extra frames, and any frame can be a reference (reference 1 = forward, reference 2 = backward or the I/P picture itself, +0x24 = 1 or 4, +0x18 = 0).

  • The inverse transform is the hardware's own, as the standard allows: an I picture differs from FFmpeg's

    in 0.7 % of the samples by one level; after 40 pictures of a GOP 1.2 % by one and a few dozen by two.

  • The map of not-coded macroblocks is one bit a macroblock, lowest bit first, saved by the hardware in

    64-bit words after a P picture (+0x2dc low half counts them) and loaded for a B picture: a B macroblock whose bit is set has no data.

  • A video packet header in front of such a macroblock is missed and the rest of the B picture is lost

    (the hardware then leaves a copy of the forward reference). The stock library knows: it scans every B picture of a stream with resync markers in software (mpeg4_preparse_bitstream) and reports the picture as broken. FFmpeg's own encoder writes a packet per slice thread, so such files are common. In a B picture a header at the start of a macroblock row with the picture's quantiser changes nothing (the vector predictors start afresh in every row), so our FFmpeg path cuts those headers and their stuffing out of B pictures before the hardware sees them (y2_cut_packet_headers; mpeg4_jobs.py does the same for the bench). The picture's closing stuffing (a zero, then ones up to the byte) must then be written again at the new bit position: the hardware checks it, and with the old bits there it reported a correct picture as failed (VLD+0x3cc = 0x03000101, 3 of 133 B pictures of a 720p film). 16 of 16, 40 of 40 and 200 of 200 pictures of multi-slice streams are right with both.

  • Quarter sample with four vectors and MPEG quantiser matrices: right. **Interlaced streams: I and P pictures

    right, B pictures wrong in a few field-predicted macroblocks**; cause not found, so interlaced MPEG-4 stays in software. Sprites (GMC), data partitioning and short headers were not tried and stay in software.

  • Reference for interlaced material: FFmpeg's software decoder is not deterministic there with frame threads

    (ffmpeg -threads 1, 4 and 16 give three different results for the same file); compare with one thread. The hardware's interlaced B pictures differ from that one too.

  • A register sweep for a diff (reading every offset of the decoder blocks) hung the player until the

    watchdog reset it. Read only what the stock library reads.

Through FFmpeg and in Reborn (test build 246, same day)

Driver call and mpeg4_y2vdec, hardware and software side by side (vdec-ffmpeg, now sample by sample), on the player: Xvid 640×480 without B pictures, 720×576 (9 Mbit/s and 1.5 Mbit/s), 720×576 with MPEG quantiser matrices, 1280×720 with quarter sample (17 Mbit/s) and at 3 Mbit/s, 1920×1080 (22 Mbit/s), FFmpeg's encoder 1280×720 in slices: 199 to 499 pictures each, every one on the hardware, largest difference 3 to 5 levels, 3 to 12 % of the samples off by any amount at the end of 200-picture GOPs. Xvid's packed B pictures (two pictures in one chunk) need nothing special: the hardware stops at the last macroblock. A film with global motion compensation and an interlaced one are refused at init and decoded in software. Decoder time a picture: 1.9 ms (640×480), 2.0 to 3.0 ms (720×576), 4.2 to 6.1 ms (1280×720), 11.4 ms (1920×1080 at 22 Mbit/s).

Still open

  • H.264: damaged streams have not been tried; top/left cropping is not applied to hardware pictures. (The

    chip type is 6 on this unit; the H.264 code has no branch on it that matters.)

  • MPEG-4: interlaced B pictures; data partitioning, sprites; damaged streams.
  • Power per picture size; sleep and wake with an open decoder.
