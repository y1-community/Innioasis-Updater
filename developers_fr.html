Pour les développeurs de firmware

Ajoutez votre micrologiciel à Updater CE.

Updater CE est le catalogue communautaire et le programme d'installation du micrologiciel personnalisé. Développez votre projet à partir d'une base ROM, publiez-le en tant que référentiel public avec les ressources de version appropriées, ajoutez les entrées de modèle à slidia_manifest.xml, testez les filtres du modèle et ouvrez une pull request. Un référentiel peut servir tous les modèles qu'il prend en charge.

Partir d'une base ROM

Les ROM de base offrent aux développeurs de micrologiciels personnalisés une base Android propre avec les puces radio sans fil activées. Sur le Y1, ils activent le Wi-Fi et le GPS aux côtés du Bluetooth et de la FM d'usine ; sur le Y2, ils activent le Wi-Fi, le GPS et la FM aux côtés du Bluetooth d'usine.

Téléchargements de base ROM pour le développement de micrologiciels personnalisés, avec la version Android et les fonctionnalités sans fil que chacun permet

rom_type_b.zipY1 · Type BAndroid 4.2.2Ajoute le Wi-Fi et le GPS au Bluetooth et à la FM d'usine (FM fonctionne déjà sur le Y1 de l'usine). Pour les lecteurs Y1 livrés avec un système d'exploitation antérieur à 2.0.0.

Ces images représentent la base Android d'origine (AOSP) avec les radios sans fil de l'appareil activées, de sorte qu'un micrologiciel personnalisé peut ajouter des fonctionnalités réseau au lieu de remplacer la pile radio. Ils constituent le point de départ pratique des étapes de publication ci-dessous.

Utilisez ces noms d'éléments de version

Le nom de fichier fait partie du signal de compatibilité. Gardez les noms exacts et placez les fichiers ZIP dans les ressources de version du projet, pas seulement dans l'arborescence des sources du référentiel.

Noms des actifs ZIP du micrologiciel et appareils pris en charge
ActifAppareilMatérielSignification

rom_type_b.zipY1Type BY1 appareils livrés avec un système d'exploitation antérieur à 2.0.0.

Ne renommez pas un package pour l’adapter à un autre modèle. Y1 et Y2 utilisent des fichiers de plate-forme MediaTek et une configuration clignotante différents. Publiez le package pour le matériel qu’il prend réellement en charge.

Comment fonctionne la connexion

Updater CE lit le manifeste comme son catalogue. Chaque <package> La ligne lui indique le nom du projet, le référentiel, le modèle et le gestionnaire. Lorsqu'un utilisateur choisit ce projet, Updater vérifie les versions publiées du référentiel et recherche un rom*.zip actif.

Manifeste

Nomme le projet et le mappe à un modèle. Y1 et Y2 nécessitent des lignes distinctes, même lorsqu'ils partagent un référentiel.

Version publiée

Contient les ressources ZIP installables. Une seule version peut contenir les packages Y1 Type A, Y1 Type B et Y2 ensemble.

Updater CE installer

Utilise le modèle sélectionné pour choisir le package correspondant et le chemin de clignotement spécifique au modèle. L'utilisateur ne devrait pas avoir à deviner le nom d'un fichier.

Publier un projet en cinq étapes

  1. Forkez le référentiel Updater CE. Créez votre propre fourchette de y1-community/Innioasis-Updater, puis clonez votre fork localement.
  2. Préparez un référentiel public de micrologiciels. Assurez-vous que le référentiel est public et que sa version contient les ressources ZIP appropriées. Vous pouvez mettre rom.zip, rom_type_b.zip, et rom_y2.zip sur la même release lorsqu'ils appartiennent à la même version.
  3. Modifiez le manifeste. Ouvert slidia_manifest.xml à la racine de votre fourchette Updater CE. Ajoutez une ligne pour chaque modèle pris en charge par la version (Y1 et Y2 sont la paire commune). Le repo la valeur est celle du référentiel owner/repository; url est la page publique du projet.
  4. Testez le catalogue. Exécutez Updater à partir de la caisse modifiée. Sélectionnez Y1 et confirmez que le projet affiche les actifs Y1. Sélectionnez Y2 et confirmez qu'il affiche la version Y2. Cochez Type A et Type B séparément lorsque les deux sont publiés.
  5. Ouvrez une pull request. Envoyez la modification du manifeste vers votre fork et ouvrez une demande d'extraction sur le référentiel Updater CE en amont. Incluez le lien du projet, les modèles pris en charge, la balise de version, les noms des actifs et les appareils que vous avez testés.

Remplissez le référentiel et cochez chaque modèle pris en charge par la version. Une version, trois atouts

          
Une version partagée peut contenir rom.zip, rom_type_b.zip, et rom_y2.zip. Updater les classe séparément et choisit parmi les filtres de modèle et de matériel.

        

        

          
Ne regroupez pas les suppositions

          
N'incluez pas de package Y1 sous le nom de fichier Y2, et n'ajoutez pas de données scatter, préchargement ou partition non testées simplement pour faire apparaître un actif.

        

      

    




      
Pourquoi les entrées de modèle sont importantes pendant le flashage

      
Le manifeste n'est pas seulement un menu de téléchargement. Après l'extraction, Updater CE utilise le modèle résolu pour préparer le chemin d'installation correspondant. Y1 et Y2 ont des fichiers de plate-forme, des préchargeurs, une configuration scatter et des dispositions de périphérique différents.

      
    
        
  • Y1: le programme de mise à jour prépare le chemin Y1 et utilise les partitions nommées du périphérique lorsque MTKClient est utilisé.
    • 
        
  • Y2: le programme de mise à jour prépare le chemin Y2 et utilise la configuration Y2 MT6582. La récupération complète peut utiliser les adresses physiques des données de dispersion correctes du modèle.
    • 
        
  • Prise en charge multiplateforme : Updater CE gère le flash natif directement sur Windows, Linux et macOS (prenant en charge les Mac Intel et Apple Silicon) sans outils de flash supplémentaires.
    • 
      

      
Les contributeurs doivent fournir des fichiers de firmware corrects, et non des décalages flash. Ne modifiez pas les adresses scatter, les préchargeurs, les fichiers DA ou les commandes de partition pour contourner un package défectueux. Corrigez l’actif de version et testez sur le modèle prévu.

    




      
Avant de demander une fusion

      
    
        
  1. Validez le XML avec un analyseur XML. Une citation ou une clôture manquante /> peut masquer chaque entrée après.
    2. 
        
  2. Lancez le programme de mise à jour depuis votre caisse afin qu'il charge le manifeste local avant l'actualisation à distance.
    3. 
        
  3. Vérifiez Y1 et Y2 indépendamment. Confirmez que le projet apparaît uniquement là où son package est pris en charge.
    4. 
        
  4. Consultez la liste des versions pour rom.zip, rom_type_b.zip, et rom_y2.zip le cas échéant.
    5. 
        
  5. Testez l'installation réelle sur l'appareil prévu, avec un câble de données USB fiable et un plan de récupération pour revenir au logiciel d'origine.
    6. 
        
  6. Dans la pull request, expliquez ce que vous avez testé. Ne décrivez pas un modèle non testé comme pris en charge.
    7.
