ファームウェア開発者向け

ファームウェアを Updater CE に追加します。

Updater CE は、カスタム ファームウェアのコミュニティ カタログおよびインストーラーです。ベース ROM からプロジェクトを開発し、正しいリリース アセットを含むパブリック リポジトリとして公開し、モデル エントリを slidia_manifest.xml、モデル フィルターをテストし、プル リクエストを開きます。 1 つのリポジトリがサポートするすべてのモデルに対応できます。

Updater CE ソースを表示する ソフトウェアのダウンロードを参照する

ベース ROM から開始します

ベース ROM は、カスタム ファームウェア開発者に、ワイヤレス無線チップが有効になったクリーンな Android 基盤を提供します。 Y1 では、工場出荷時の Bluetooth と FM に加えて、Wi-Fi と GPS が有効になります。 Y2 では、工場出荷時の Bluetooth に加えて Wi-Fi、GPS、FM が有効になります。

カスタム ファームウェア開発用のベース ROM ダウンロード。Android バージョンとそれぞれで有効になるワイヤレス機能が含まれます。

接続の仕組み

Updater CE はマニフェストをカタログとして読み取ります。それぞれ <package> この行は、プロジェクト名、リポジトリ、モデル、およびハンドラーを示します。ユーザーがそのプロジェクトを選択すると、アップデータはリポジトリの公開リリースをチェックし、 rom*.zip 資産。

マニフェスト

プロジェクトに名前を付け、モデルにマップします。 Y1 と Y2 は、リポジトリを共有する場合でも、別々の行が必要です。

公開されたリリース

インストール可能な ZIP アセットが含まれています。 1 つのリリースには、Y1、Type A、Y1、Type B、および Y2 のパッケージが一緒に含まれる場合があります。

Updater CE インストール

選択したモデルを使用して、一致するパッケージとモデル固有のフラッシュ パスを選択します。ユーザーはファイル名を推測する必要はありません。

5 つのステップでプロジェクトを公開する

  1. Updater CE リポジトリをフォークします。 独自のフォークを作成する y1-community/Innioasis-Updater、ローカルでフォークのクローンを作成します。
  2. パブリックファームウェアリポジトリを準備します。 リポジトリがパブリックであり、そのリリースに正しい ZIP アセットが含まれていることを確認してください。置くことができます rom.zip, rom_type_b.zip、そして rom_y2.zip 同じバージョンに属している場合は、同じリリース上で実行されます。
  3. マニフェストを編集します。 開く slidia_manifest.xml Updater CE フォークのルートにあります。リリースがサポートするモデルごとに 1 行を追加します (Y1 と Y2 が共通のペアです)。の repo 値はリポジトリの値です owner/repository; url 公開プロジェクトページです。
  4. カタログをテストします。 編集したチェックアウトからアップデーターを実行します。 Y1 を選択し、プロジェクトに Y1 アセットが表示されていることを確認します。 Y2を選択し、Y2のリリースが表示されていることを確認します。 Type AとType Bが両方公開されている場合は個別に確認してください。
  5. プルリクエストを開きます。 マニフェストの変更をフォークにプッシュし、上流の Updater CE リポジトリに対してプル リクエストを開きます。プロジェクトのリンク、サポートされているモデル、リリース タグ、アセット名、テストしたデバイスを含めます。

マニフェストが読み取るすべての属性

      
これらは、現在の Updater CE ビルドが理解する属性です。ジェネレーターは、ユーザーが入力したもののみを書き込みます。アプリは残りの部分について適切なデフォルトに戻ります。

      

        

          slidia_manifest.xml パッケージの属性とその意味
          
            
属性必要です何をするのか

          
          
            
nameはいカタログおよびインストールカードに記載されているソフトウェア名。

            
repoはいowner/repo。アプリはそのリポジトリの GitHub リリースを読み取ります。

            
deviceはい対象モデル、大文字(Y1, Y2, G1, Q3e、…）。モデルごとに 1 つのエントリを保持します。

            
url推奨カタログから開いたプロジェクト ページまたはリリース ノート。

            
type, handlerはい、実際にはtype="img" そして handler="Custom Firmware"。他のタイプおよび非ファームウェア ハンドラーはスキップされます。

            
brandオプションカタログブランド（Innioasis, Timmkoo）。 Empty では、モデルのデフォルトのブランドが使用されます。

            
package_nameオプションリリースアセットのファイル名。デフォルトは rom.zip Y1 と rom_<model>.zip 他のモデルでは。

            
asset_patternオプションファームウェア zip に名前が付けられていないリリースでは、大文字と小文字を区別しない glob rom*.zip （例えば my-firmware-*.zip).

            
type_a_asset, type_b_assetオプションファイル名に通常のマーカーが含まれていない場合に、Y1 Type A および Type B zip を識別するグロブ。

            
iconオプションロゴの URL。リリース独自の後に使用される updater.png / updater.jpg、そしてすべてのリリースのフォールバックとして。

            
icon_darkオプションダークテーマのロゴ。 image_dark は受け入れられるエイリアスです。

            
imageオプション二次的なライト アートワーク、その後に試行 icon.

            
post_install, post_install2オプションインストールが成功した後に開かれたページ。 2 番目のガイドでは、複数のステップのガイドについて説明します。

            
portable_zipsオプションカンマ区切り *-mirror すぐに実行できるポータブル パッケージを公開するリポジトリ。

            
derivativeオプションファームウェアの構築元となるリポジトリ。同じ派生ルートを持つファームウェアはユーザー データを保持できます。

            
info_repoオプションリリースには、ファームウェアが展開する内容が記述されているアプリ リポジトリ。必要 post_install または post_install2.

            
apk_repoオプションファームウェアの後にアプリが APK インストールされるアプリ リポジトリ。

            
min_versionオプションUpdater CE がこのバージョンより古い場合、エントリを非表示にします。

            
do_not_keep_dataオプションtrue （また 1 / yes) このファームウェアのデータ保持を完全にブロックします。

            
slugオプションリンクと保存されたインストール レコードの安定した識別子。空の場合は名前とモデルから生成されます。

            
descriptionオプションカタログの短い説明。属性値または要素のテキストにすることができます。

          
        

      

      
互換性を確保するために、従来の名前も引き続き読み取られます。 model, package, portable_zip, post_install_2, min_app_version そして image_dark。新しいエントリには上記の現在の名前を使用する必要があります。

1 つのリリース、3 つのアセット

          
共有リリースには以下を含めることができます rom.zip, rom_type_b.zip、そして rom_y2.zip。アップデーターはそれらを個別に分類し、モデルとハードウェアのフィルターから選択します。

        

        

          
推測をまとめないでください

          
Y2 ファイル名の下に Y1 パッケージを含めたり、アセットを表示するためだけに未テストのスキャッター、プリローダー、またはパーティション データを追加したりしないでください。

        

      

    




      
フラッシュ中にモデルのエントリが重要な理由

      
マニフェストは単なるダウンロード メニューではありません。抽出後、Updater CE は解決されたモデルを使用して、一致するインストール パスを準備します。 Y1 と Y2 には、異なるプラットフォーム ファイル、プリローダー、スキャッター構成、デバイス レイアウトがあります。

      
    
        
  • Y1: アップデーターは Y1 パスを準備し、MTKClient が使用される場合にデバイスの名前付きパーティションを使用します。
    • 
        
  • Y2: アップデーターは Y2 パスを準備し、Y2 MT6582 構成を使用します。完全リカバリでは、モデルが正しい散乱データからの物理アドレスを使用できます。
    • 
        
  • クロスプラットフォームのサポート: Updater CE は、追加のフラッシュ ツールを使用せずに、Windows、Linux、macOS (Intel と Apple Silicon Mac の両方をサポート) 全体でネイティブ フラッシュを直接処理します。
    • 
      

      
貢献者は、フラッシュ オフセットではなく、正しいファームウェア ファイルを提供する必要があります。 不正なパッケージを回避するためにスキャッタ アドレス、プリローダー、DA ファイル、またはパーティション コマンドを編集しないでください。リリース アセットを修正し、目的のモデルでテストします。

    4. 
        
  4. リリースリストを確認してください rom.zip, rom_type_b.zip、そして rom_y2.zip 該当する限り。
    5.

    6. 
        
  6. プル リクエストでは、テストした内容を説明します。テストされていないモデルをサポートされていると説明しないでください。
    7.
